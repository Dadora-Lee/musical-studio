2. 개발 환경 선택 — WSL2 강력 권장

당신의 OS에 따라:

  • macOS / Linux: 기본 터미널 사용. WSL 불필요. → Step 1로
  • Windows: WSL2 강력 권장. 아래 비교 후 결정.

Windows 사용자 — WSL2 vs Native Windows

✅ WSL2 (Ubuntu) — 강력 권장

  • HMR 10배 빠름: NTFS의 inotify 오버헤드 없음
  • Owner와 동일 환경: 환경 차이 버그 0
  • CI와 동일: GitHub Actions가 Linux. 본인 PC와 CI 결과 일치
  • pnpm/git/gh CLI native: Path 구분자 문제 없음
  • Supabase CLI 정상 동작 (Windows는 일부 이슈)
  • Docker WSL Integration 그대로 사용
  • Microsoft 공식 권장

⚠ Native Windows (PowerShell + Node)

  • HMR 10배 느림 (큰 프로젝트일수록 심각)
  • Path 구분자(\ vs /) 미묘한 버그 가능
  • Supabase CLI 호환성 이슈 (일부 명령)
  • CI 결과 ≠ 본인 PC 결과 → 디버그 어려움
  • 장점: WSL 설치 단계 SKIP
결론: Windows 사용자는 WSL2 설치 + 그 안에서 모든 작업이 표준입니다. Owner도 같은 방식으로 진행 중이며, 본 프로젝트의 모든 자동화 스크립트가 WSL2 Linux 기준입니다.
주의 (AI Agent에게): Partner가 Windows + WSL2 선택 시, AI Agent는 모든 작업을 WSL2 Ubuntu 안에서 수행해야 합니다. /mnt/c/는 NTFS와 동일하게 느리므로 절대 사용 금지. 반드시 ~/projects/musical-studio (ext4) 사용.

3. SSH key 작동 메커니즘 (이해하고 진행)

SSH key는 비대칭 암호화로 비밀번호 없이 안전한 접속을 제공합니다. 본 프로젝트에서 흐름은:

[Partner 본인 PC] [github.com] [Owner WSL dev server] ───────────────── ──────────── ────────────────────── ssh-keygen → 키쌍 생성: ~/.ssh/id_ed25519 (개인키, 비밀) ~/.ssh/id_ed25519.pub (공개키) ───── Step 4 ─────→ 공개키를 등록: github.com/settings/ssh ←─── Step 5 (Owner) ── ssh-import-id gh:<name> URL fetch: github.com/<name>.keys → 공개키를 가져와 ~/.ssh/authorized_keys 에 추가 SSH/SCP 연결 시도 ────── Step 6 (AI Agent) ─────────────────→ ssh -p 2222 soswolf@... Owner의 SSH 서버: "Partner의 개인키 challenge" 개인키로 답신 ←──────────────────────────────────── "authorized_keys에 있다 ✓" ↓ 접속 허용 → SCP 가능

핵심 포인트

  • 공개키는 공개해도 안전: github.com/<username>.keys 는 누구나 볼 수 있는 URL.
  • 개인키는 절대 노출 금지: 본인 PC의 ~/.ssh/id_ed25519는 본인만 보관.
  • Owner의 ssh-import-id는 fetch 시점의 키만 가져옴: Partner가 키 등록 전에 Owner가 실행하면 빈 결과 → Partner 등록 후 Owner가 한 번 더 실행 필요.
  • Owner는 GitHub 외부에서 따로 키를 받을 필요 없음: github.com/<partner>.keys URL에서 자동 fetch.
현재 상태: Owner가 이미 ssh-import-id gh:jieun0610을 실행했으나, 그 시점에 당신의 SSH key가 GitHub에 등록되어 있지 않아서 빈 결과로 끝났습니다. Step 4 끝낸 뒤 Step 5에서 Owner에게 알려주시면 Owner가 한 번 더 실행하여 등록 완료됩니다.

Step 4. SSH key 생성 + GitHub 등록 YOU

⚠중요 — SSH key 등록 안 하면 dev server 시크릿 받기 불가

이 단계 완료해야 Owner가 인증 등록할 수 있고, AI Agent가 시크릿(SCP)을 받을 수 있습니다.

1기존 SSH key 확인

본인 환경의 터미널 (Windows는 WSL Ubuntu, macOS/Linux는 기본 터미널):

ls ~/.ssh/id_ed25519.pub 2>/dev/null && echo "기존 키 있음" || echo "없음 — 생성 필요"

2SSH key 생성 (없으면)

ssh-keygen -t ed25519 -C "your-email@example.com"
# 1) 파일 경로: 그냥 Enter (기본 ~/.ssh/id_ed25519)
# 2) Passphrase: 빈 칸 Enter (또는 본인 passphrase — 기억해야 함)
# 3) 확인: 다시 Enter

생성 확인:

ls ~/.ssh/id_ed25519 ~/.ssh/id_ed25519.pub

3공개키 내용 복사

cat ~/.ssh/id_ed25519.pub

출력 전체 복사 (시작이 ssh-ed25519 ...). 다음 단계에서 붙여넣기.

4GitHub에 공개키 등록

  1. github.com/settings/ssh/new
  2. Title: musical-studio-partner
  3. Key type: Authentication Key (기본)
  4. Key: 위에서 복사한 공개키 붙여넣기
  5. Add SSH key

✓등록 검증

아래 URL에서 본인 공개키가 보이면 OK:

curl https://github.com/<본인-github-username>.keys

예: curl https://github.com/jieun0610.keys

📡 AI 에이전트 협업 조율 시스템 (합류 후 매 세션) AI

i왜 필요한가

2명의 개발자가 다른 AI 에이전트(Claude/Antigravity/Codex)로 동시 작업하므로 서로의 작업을 자동으로 인지해야 합니다. GitHub Actions가 자동 처리.

1자동 동작 (당신이 신경 쓸 일 X)

당신 또는 Owner가 main에 push하면:

  1. GitHub Actions가 변경 사항을 AI(GitHub Models)로 요약
  2. docs/agent-log/YYYY-MM-DD.md에 자동 append + bot commit
  3. 다른 사람이 다음 세션 시작 시 git pull 하면 자동 인지

2당신의 AI Agent가 매 세션 시작 시 자동 실행

cd ~/projects/musical-studio
git pull --rebase origin main

# 오늘 다른 agent가 한 일
cat docs/agent-log/$(date -u +%Y-%m-%d).md 2>/dev/null

# 미해결 인수인계 — 반드시 확인
ls docs/agent-handoff/open/ 2>/dev/null

3당신의 AI Agent가 매 세션 종료 시 자동 처리

  • 미해결 작업 있으면 → docs/agent-handoff/open/YYYY-MM-DD-<slug>.md 작성 후 commit
  • 새 architectural 결정 있으면 → docs/agent-decisions/YYYY-MM-DD-<slug>.md 작성
  • commit message에 Co-Authored-By: <Agent Name> trailer
  • git push → GitHub Actions가 알아서 다른 agent용 요약 append
중요: docs/agent-log/는 GitHub Actions가 자동 관리. AI Agent가 직접 쓰지 말 것 (무한 루프 방지를 위해 paths-ignore 처리됨).

FAQ + Troubleshooting

Q1. PAT를 AI Agent 채팅창에 입력해도 안전한가요?

정식 AI Agent(Claude Code, Antigravity, Codex CLI)는 PAT를 메모리에만 두고 파일로 저장하지 않습니다. 추가 보안 원하면 프롬프트에 PAT 칸은 빈 값으로 보낸 뒤, AI가 멈추면 본인이 직접 터미널에서 gh auth login --with-token을 실행 (stdin 입력).

Q2. Step 5 Owner 알림 없이 Step 6 진행하면 어떻게 되나요?

AI Agent가 SCP로 dev server에 접속 시도 → Permission denied (publickey) 에러로 실패. AI가 멈추고 Owner 확인 요청. 그 때 Step 5 메시지 보내고 Owner 응답 받은 뒤 AI에게 "재시도" 알려주면 됨.

Q3. 기존 작업물이 있는데 어떻게 통합되나요?

AI가 본 가이드의 partner-bootstrap.md 섹션 3/4의 시나리오 따라 자동 진행. 핵심:

  • 당신의 작업물을 새 branch ai/<agent>/partner-initial-work로 옮김
  • main과 충돌 가능한 부분은 AI가 멈추고 확인 요청
  • Draft PR 생성 → Owner와 review 후 머지

Q4. Dev server에 SCP가 계속 안 됩니다

다음 순서로 확인:

  1. 본인 SSH key가 GitHub에 등록됐는지 (Step 4 검증 URL)
  2. Owner가 ssh-import-id를 재실행했는지 (Step 5)
  3. SSH 연결 자체가 되는지: ssh -v -p 2222 soswolf@musicalstudio.freedynamicdns.net 결과 보고
  4. 그래도 안 되면 대안: Owner가 Bitwarden/1Password로 .env/secrets.env 텍스트 직접 공유. 본인 PC의 메모장으로 붙여넣기.

Q5. WSL을 진짜 꼭 써야 하나요? Native Windows로 가면 안 되나요?

Native Windows로 진행해도 작동은 합니다. 단:

  • HMR 10배 느림 (특히 큰 변경 시 5-10초 대기)
  • 본 프로젝트의 자동화 스크립트(scripts/setup.sh, sync-env.sh 등)는 bash 스크립트. PowerShell 변환 작업 필요
  • CI(GitHub Actions) Linux와 결과 다름 → "내 PC에선 됐는데 CI에서 깨짐" 발생

이 trade-off를 감수할 의향이 있고 어차피 본인 PC에 WSL 깔기 싫으면 Native Windows로 진행 가능. AI Agent에게 운영체제 정보를 정확히 알려주면 그에 맞춰 진행.

Q6. 기존 musical-studio 작업물이 어디 있는지 모르겠어요

find ~ -name "musical-studio" -type d 2>/dev/null
find ~ -name "package.json" -path "*musical*" 2>/dev/null

없으면 "없음"으로 답하면 됩니다.

Q7. 합류한 뒤 어디서 일상적으로 작업하나요?

본인 PC의 WSL Ubuntu 안의 ~/projects/musical-studio 디렉토리가 당신의 메인 작업 공간입니다. Owner의 dev server (port 3000)는 통합 테스트/모바일 QA용으로 별도 활용. 자세한 워크플로는 dev-workflow.html 참조.
