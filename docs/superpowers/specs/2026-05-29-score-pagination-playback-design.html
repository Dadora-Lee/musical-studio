악보 페이지 분할 및 재생 설계

배경

현재 /work 화면은 서버에서 실제 MusicXML을 읽고 ScoreViewer 클라이언트 컴포넌트가 OSMD로 악보를 렌더링한다. 다음 단계의 목표는 악보를 한 화면에 길게 표시하는 대신 보기 좋은 페이지 단위로 탐색하게 만들고, 연습자가 MR, AR, 악보재생을 구분해서 사용할 수 있게 하는 것이다.

프로젝트 규칙상 MusicXML 처리는 src/lib/musicxml/을 중심으로 유지하고, 악보 렌더링은 OSMD를 사용한다. Soundslice는 런타임 의존성으로 사용하지 않는다.

목표

  • 악보 영역에 페이지 단위 탐색 UI를 추가한다.
  • MR, AR, 악보재생을 독립적인 재생 소스로 제공한다.
  • MVP에서는 MR/AR은 실제 오디오 트랙 재생의 기준으로 두고, 악보재생은 별도 확인 모드로 둔다.
  • 이후 녹음 동기화와 마디 단위 반복으로 확장할 수 있게 재생 상태와 렌더링 책임을 분리한다.

비목표

  • 이번 단계에서 MR, AR, 악보재생을 완전 동기화하지 않는다.
  • 이번 단계에서 녹음 파일과 악보 커서를 정밀하게 매핑하지 않는다.
  • 이번 단계에서 MusicXML 기반 전체 오케스트레이션 품질을 완성하지 않는다. 악보재생은 파트/음 확인용 기능으로 시작한다.
  • 새 외부 악보 서비스나 Soundslice API를 도입하지 않는다.

접근안

접근안 A: 단일 Transport + 소스 선택

하단 transport는 하나만 유지하고, 재생 소스를 MR, AR, 악보 세그먼트로 선택한다. 선택된 소스에 따라 재생/일시정지/정지/이동 버튼과 볼륨 조절이 같은 위치에서 동작한다.

장점은 UI가 가장 단순하고 현재 /work 화면 구조를 크게 흔들지 않는다는 점이다. 단점은 악보재생이 MR/AR과 내부 구현 방식이 다르기 때문에 컴포넌트 내부에서 재생 엔진을 명확히 분리해야 한다.

접근안 B: MR/AR Transport와 악보재생 Transport 분리

MR/AR 오디오 컨트롤은 기존 하단 transport에 두고, 악보재생 컨트롤은 악보 영역 상단 또는 악보 패널 안에 별도로 둔다.

장점은 악보재생이 실험적인 동안 안전하다는 점이다. 단점은 화면의 컨트롤이 늘어나고 배우가 어떤 재생 버튼을 눌러야 하는지 헷갈릴 수 있다.

접근안 C: 3트랙 동시 타임라인

MR, AR, 악보재생을 모두 별도 트랙으로 표시하고 DAW처럼 동시 재생/비교할 수 있게 만든다.

장점은 장기적으로 강력하다. 단점은 prototype 단계에는 무겁고, 동기화 기준과 UX 복잡도가 커진다.

결정

MVP는 접근안 A를 사용한다. UI는 하나의 transport를 유지하되 재생 소스를 MR, AR, 악보로 선택하게 만든다. 내부 구현은 audio 재생과 score 재생을 분리해서, 나중에 동기화 기능을 추가할 때 구조를 갈아엎지 않게 한다.

화면 설계

악보 패널 상단에는 페이지 탐색 바를 둔다.

  • 이전 페이지 버튼
  • 현재 페이지 / 전체 페이지 표시
  • 다음 페이지 버튼
  • 전체 보기 토글 또는 맞춤 보기 토글은 후순위로 둔다.

악보 본문은 OSMD가 렌더링한 SVG를 페이지 단위로 보여준다. OSMD가 생성한 페이지 DOM을 기준으로 현재 페이지 외의 페이지를 숨기거나, OSMD 렌더링 옵션이 충분하면 page format을 조정해서 한 페이지 단위가 자연스럽게 나오도록 한다.

하단 transport에는 소스 선택 세그먼트를 둔다.

  • `MR`: MR 오디오 파일을 재생한다.
  • `AR`: AR 오디오 파일을 재생한다.
  • `악보`: MusicXML 기반 재생을 실행한다.

선택된 소스는 같은 transport 버튼을 사용한다.

  • 10초 전 또는 이전 위치
  • 재생
  • 일시정지
  • 정지
  • 10초 후 또는 다음 위치
  • 볼륨

악보재생 모드에서 10초 이동은 정확한 시간 매핑이 생기기 전까지 이전/다음 마디 또는 이전/다음 커서 위치로 해석한다.

컴포넌트 설계

`ScoreViewer`

역할은 OSMD 인스턴스 생성, MusicXML 로드, 렌더링 완료 이벤트 전달이다. 페이지 분할을 위해 렌더링 후 OSMD 컨테이너 DOM 또는 OSMD metadata에서 페이지 수를 계산해 상위 컴포넌트에 전달한다.

필요 props 후보:

  • `source`: 기존 유지
  • `currentPage`: 현재 표시할 페이지
  • `onPageCountChange`: 전체 페이지 수 전달
  • `onReady`: 기존 유지, score playback engine이 OSMD cursor를 연결할 수 있게 한다.

`ScorePager`

악보 페이지 상태를 관리한다. 현재 페이지, 전체 페이지 수, 이전/다음 이동을 담당한다. UI는 악보 패널 상단에 붙인다.

`PracticeTransport`

MR, AR, 악보 중 현재 재생 소스를 선택하고 공통 버튼을 제공한다. 실제 재생 구현은 source별 controller에 위임한다.

`useAudioPlayback`

MR/AR 파일 재생을 담당한다. HTMLAudioElement 기반으로 시작한다. 나중에 녹음 동기화가 들어오면 MR을 기준 타임라인으로 확장한다.

`useScorePlayback`

악보재생을 담당한다. 첫 단계에서는 OSMD cursor를 사용해 현재 위치를 이동시키고, Tone.js 기반의 단순 음 재생은 가능한 범위에서 얹는다. MusicXML 음정/박자 해석이 충분하지 않은 경우에는 “커서 재생”을 먼저 제공하고 소리 재생은 다음 단계로 분리한다.

데이터 흐름

1. 서버 페이지가 active Number의 MusicXML, MR, AR URL 또는 prototype path를 준비한다.

2. `ScoreViewer`가 MusicXML raw string을 받아 OSMD로 렌더링한다.

3. 렌더링 완료 후 OSMD 인스턴스가 `onReady`로 전달된다.

4. `ScorePager`는 전체 페이지 수와 현재 페이지를 관리한다.

5. `PracticeTransport`는 선택된 소스에 따라 `useAudioPlayback` 또는 `useScorePlayback`을 호출한다.

6. 녹음 기능은 추후 MR 소스를 기준으로 같은 transport/timeline에 연결한다.

오류 처리

  • MusicXML 로딩 실패: 악보 패널에 실패 메시지와 파일명을 표시한다.
  • OSMD 렌더링 실패: `ScoreViewer`의 기존 오류 UI를 유지하되, source file label도 함께 표시한다.
  • MR/AR 파일 없음: 해당 소스 버튼은 비활성화하고 “파일 미등록” 상태를 표시한다.
  • 악보재생 미지원 MusicXML 구조: 악보 표시는 유지하고, 악보재생 버튼에 “커서 재생만 가능” 상태를 표시한다.

테스트 계획

  • `ScoreViewer`가 `onPageCountChange`를 호출하는지 단위 테스트한다.
  • `ScorePager`의 이전/다음 버튼이 경계를 넘지 않는지 테스트한다.
  • `PracticeTransport`에서 MR/AR/악보 소스 선택이 바뀌는지 테스트한다.
  • MusicXML 파일이 있는 `/work` 페이지가 `osmd-canvas`를 렌더링하는지 확인한다.
  • 수동 확인으로 `SONG07_거짓말이아니야` 악보가 페이지 단위로 탐색되는지 확인한다.

구현 순서

1. `ScoreViewer`에 페이지 수 계산과 현재 페이지 표시 제어를 추가한다.

2. `ScorePager`를 만들고 `/work` 악보 패널에 붙인다.

3. `PracticeTransport`를 분리하고 MR/AR/악보 소스 선택 UI를 만든다.

4. MR/AR은 HTMLAudio 기반으로 재생 상태만 먼저 연결한다.

5. 악보재생은 OSMD cursor 기반으로 먼저 연결한다.

6. Tone.js 음 재생은 MusicXML 해석 범위를 확인한 뒤 별도 작은 단계로 확장한다.

열린 결정

악보재생의 첫 구현은 “커서 이동만”으로 시작할지, “단순 음 재생까지” 포함할지 구현 직전에 다시 확인한다. 다만 UI 구조는 둘 다 수용할 수 있게 설계한다.
