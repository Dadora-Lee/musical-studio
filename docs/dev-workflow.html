⚙️ 개발 워크플로

로컬에서 빠르게 개발, dev server는 통합 테스트·QA·데모 전용.

📌 결론

Local-First — 둘 다 자기 PC에서 빠른 iteration, dev server는 모바일 QA · 데모 · 디버그 페어링용.

이유: AI 멀티 에이전트 환경에선 동시 작업 충돌 회피가 최우선. 빠른 HMR, 각자 worktree, 같은 Supabase DB로 협업.

Local vs SSH-only 비교

시나리오Local-First (채택)SSH-only
두 명이 동시 작업✅ 충돌 0⚠ 같은 dev server 경합
HMR 속도⚡ 즉시🐢 네트워크 latency
AI 에이전트 병렬✅ 3 worktree 동시⚠ shell 경합
본인 PC 꺼졌을 때✅ 영향 없음❌ dev server 중단
환경 일관성⚠ OS 차이 가능✅ 동일 환경
통합 테스트·모바일dev server에 합류✅ 자연스러움

역할 분담

🖥️ 각자 PC (Local-First)

  • 실제 코딩
  • HMR 빠른 iteration
  • Unit/Integration 테스트
  • git worktree 작업
  • PR 작성

🌐 Dev Server (Owner WSL)

  • main 브랜치 hosting
  • 통합 환경 (모두 같은 Supabase DB)
  • 모바일 QA (DDNS hostname)
  • 외부 데모 (배우 3-5명 테스트)
  • SSH 페어 프로그래밍 (옵션)

표준 일일 워크플로 (양 개발자 공통)

# 자기 PC에서
cd ~/projects/musical-studio
git pull --rebase origin main

# 작업 worktree
git worktree add -b ai// ../musical-studio- main
cd ../musical-studio-

# 로컬 dev (자기 localhost:3000)
pnpm dev

# 테스트
pnpm test            # vitest
pnpm test:e2e        # playwright

# 푸시 + PR
git push -u origin ai//
gh pr create --draft

# 머지 후 정리
cd ../musical-studio
git worktree remove ../musical-studio-

Dev Server 접속

1. 브라우저 (테스트/데모)

# 같은 LAN: http://192.168.31.101:3000?token=<DEV_ACCESS_TOKEN>
# 다른 LAN: http://musicalstudio.freedynamicdns.net:3000?token=<DEV_ACCESS_TOKEN>
# 모바일: 위 URL 그대로

첫 접속 시 ?token=... 쿼리 → 쿠키로 저장 → 이후 자동.

2. SSH (디버그/페어링)

ssh -p 2222 soswolf@musicalstudio.freedynamicdns.net
cd ~/projects/musical-studio
git pull
pkill -f "next dev"
pnpm dev --hostname 0.0.0.0 &

자세한 SSH 가이드: ssh-guide.html

환경변수 (.env) 동기화

마스터: .env/secrets.env (gitignored) — Owner가 관리.
Next.js 자동 로드: .env.local — scripts/sync-env.sh로 자동 생성. 
# Owner가 secrets.env 수정 후
bash scripts/sync-env.sh
pkill -f "next dev" && pnpm dev &     # 새 env로 재시작

# Partner가 자기 PC에 secrets.env 받았을 때
# (Owner가 Bitwarden/1Password로 공유)
cp ~/secrets-from-owner.env .env/secrets.env
bash scripts/sync-env.sh
pnpm dev

DB 일관성

본인+파트너+dev server 모두 같은 Supabase 클라우드 프로젝트를 가리킴.

  • 한 명이 추가한 데이터를 다른 명이 즉시 봄
  • 마이그레이션은 Owner만 실행 (supabase db push)
  • RLS로 사용자별 권한 분리
파괴적 작업 금지: DROP TABLE, TRUNCATE 등은 PR + 양방 review 후 Owner가 실행.
